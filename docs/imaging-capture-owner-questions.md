# Owner questions: native intraoral capture (CAP)

Every question the native intraoral capture work leaves open for the office owner, in one list, in the format of `docs/owner-questions.md` on main. It is meant to be added there as a section after "Imaging" (its M2-IMG 2 is cross-referenced here, not repeated); until then, this file is the list. Each Today line was checked against the code on `cap/cap-4` (c7dd54cb8) on 2026-11-01; the lines about bit depth and the 16-bit filing route were updated for the owner's decisions of 2026-11-01, and for how CAP-16 1 and CAP-16 2 were settled that day (see Not asked here), and checked against `cap/bits-16` (CAP-16) the same day.

It covers CAP-TW (the TWAIN library inside the program), CAP-0 (the clinic runbook), CAP-1 (safer sensor capture on today's Mount/Acquire), CAP-2 (the camera in the Video window), CAP-3 (16-bit DICOM and Test capture) and CAP-4 (the capture session window, unassigned captures, Capture settings and standard templates), plus the owner rows of section 15 of the capture design ("CAP design 18" is row 18). The design is [imaging-capture-design.md](imaging-capture-design.md), a neutral edition: the clinic's vendor products and the private driver project are named by their role only. Each question names the package note and its decision number (for example "CAP-4 3"); CAP-TW and CAP-1 have no numbered decisions, so their points are named by topic. PS2-3 and PS2-4 are two CAP-4 review findings that its note leaves partly open, and "CAP-4 left open" names the rest of that note's open items. The capture session is dormant: the three-line hook in Mount/Acquire is on main since 2026-11-01, but the session is off by default ([Session] Enabled=0 in capture.ini, each computer's capture settings file), so Mount/Acquire keeps running the older way. Its setup windows (Capture settings, Test capture, Unassigned captures, Add standard templates) can be opened from Setup's Imaging Devices windows once the branches are merged. Nothing has run on a real sensor or camera yet, and none of the new windows has been opened on screen; the database code has run in 55 database-backed tests (tests/ImagingCaptureTests/Db). Each **Today:** says what the code does once it runs.

**[BEFORE PATIENT USE]** marks a question to settle before [Session] Enabled is turned on for real patients. **[BEFORE 16-BIT]** marks one to settle before a computer that captures for patients is set to Allow16Bit=1 (16 bits are the default since 2026-11-01, so a passed Test capture record for the sensor is then what lets the session store 16-bit X-rays for patients).

Two terms used below. **Unassigned captures** (the quarantine) is a folder on each computer for X-rays that reached the program but could not be filed to a patient, for example after a failed save or a patient change. **Safe disable** means the sensor software reports that turning the sensor off cannot lose an exposure; without it, the program never turns the sensor off on its own, except when the program closes or logs the user off.

## Before patient use

- **[BEFORE PATIENT USE]** (CAP design 18) Regulatory stance. The program is built as image management only: it never sets exposure, trigger, calibration or image processing, and never changes camera settings. It does start and stop the sensor software (for each slot, and on cancel, time limits, idle and patient change) and chooses the transfer and video formats. The design asks you to send these to counsel, with the 16-bit "For Presentation" label, the brightness window the program computes, and the 16-bit polarity and byte-order options, plus two questions: who is responsible for the acquisition software, since the sensor software used here is the driver project's own program and no clearance record was found for the clinic's sensor; and whether the computed window falls under 21 CFR 892.2050. Confirm the stance and send it? **Today:** built that way; nothing has gone to counsel; the session is off by default. Since 2026-11-01 the session asks for 16 bits by default, but takes them only after a Test capture passed (see 16-bit X-rays and DICOM).
- **[BEFORE PATIENT USE]** (CAP design 18) The patient-use gate also needs written pass criteria: image quality on a test phantom compared with the current imaging program's own image (for example visible line pairs and distinguishable steps), and orientation against lead markers on the phantom. Please agree them with the developer before the clinic run; patient use then waits for your sign-off against them and for the driver project's own comparison. **Today:** no criteria are written, and nothing has run on the sensor.
- **[BEFORE PATIENT USE]** (CAP design 8) 8-bit X-rays from the capture session are saved as lossless gray PNG files, much smaller than the TIFF files the older Mount/Acquire saves. They display and attach to claims like other images. Confirm PNG? **Today:** built that way for the session; the older loop still saves TIFF.
- **[BEFORE 16-BIT]** (CAP design 8, CAP-3 5, CAP-3 6) A 16-bit X-ray would be stored as a DICOM intraoral X-ray file (DICOM is the standard medical image format) labelled "For Presentation": the brightness window the program computes is part of the image as shown, and the file records that the pixels are the sensor's original. The patient's name, ID, birth date and sex are left empty in the file, so it never disagrees with the database; any later export must fill them in. Each mount is one DICOM study and each session one series. The other label, "For Processing", is the fallback if counsel prefers it. Confirm? **Today:** built that way. 16 bits are the default since 2026-11-01, so the session stores such files once a Test capture has passed for the sensor; computers that capture for patients stay at `Allow16Bit=0` until counsel has reviewed this label and the computed window and the clinic run has signed off (runbook section 14). Attaching a DICOM X-ray to a claim (as an 8-bit copy with the stored window) is not on this branch; it lands on main in the same merge step, before any release (CAP-16 1 under Not asked here). The files and their anatomy codes have not been checked with an outside DICOM validator.
- **[BEFORE PATIENT USE]** (CAP-4 6) Deliberate start. The "Start X-rays for <name>" button works only from 2 s after the patient banner appears, and a separate Confirm key (none is set up by default) starts only when held about 1 s. Keys and foot pedals set up for Retake, Skip and the like never start anything. After the first start the next slot starts by itself; every restart after a stop needs the deliberate start again. Before every start, and before an image the sensor software delivers again is placed, the program checks that the main window still shows the same patient. Enough? **Today:** built that way.
- **[BEFORE PATIENT USE]** (CAP-4 5, CAP-4 PS2-3) Stopping without safe disable. Disable and End first show "If an exposure was just taken, wait until it appears before cancelling", and a second press within 10 s stops. Closing the window (X, Alt+F4, the taskbar) follows the same rule while the sensor software is open; only an automatic logoff or the program closing forces the window closed. There are no message boxes. Once the sensor software is already stopping, X closes the window at once; the mount is kept and images that still arrive go to unassigned captures. Acceptable? **Today:** built that way.
- **[BEFORE PATIENT USE]** (CAP-4 9) A failed save (disk, network share, database) pauses the session: the image goes to unassigned captures, a red strip says why, the error sound plays, and nothing more is taken until someone presses Start again. Confirm? **Today:** built that way.
- **[BEFORE PATIENT USE]** (CAP-4 10) Automatic logoff. The session counts each start, status change, received image and key or pedal press as activity, so a series run with the pedal is not logged off. There is no timer: a session left waiting with nobody pressing anything can still be logged off, which stops it, and later images go to unassigned captures. The runbook's rule stays: each capture user's logoff time must be longer than the longest series. Acceptable? **Today:** built that way.
- **[BEFORE PATIENT USE]** (CAP design 23) Batch capture (the "Twain Multi" device type, which delivers all images at the end) is not used on tooth-labelled mounts for patients until there is a review step after the batch, because one skipped or repeated exposure shifts every later image to the wrong teeth. Confirm? **Today:** the capture session runs only for "Twain Radiograph" devices. A Twain Multi device still runs the older batch loop, which nothing blocks; the runbook allows it only on the phantom.

## Unassigned captures and recovery

- **[BEFORE PATIENT USE]** (CAP-4 3, CAP design 19, CAP-4 left open) Unassigned captures are kept on each computer, outside the shared image folder, and every Windows user of that computer sees the same folder. Assign (Image Create permission) files an image only to the patient it was taken for (into its slot if that is still empty, otherwise as "Recovered: <slot>"). Images from the older Mount/Acquire do not know their patient and can only be reassigned. Reassign needs Image Edit, a patient search (no patient is preselected) and a typed reason; Discard needs Image Delete and is logged first. Nothing is ever deleted: filed and discarded files move to a "quarantine-resolved" folder on that computer with a note of what was done, when, by whom, and for which patient and document, and neither folder is ever emptied. Confirm these rules? And when may an administrator remove resolved files (a retention period)? **Today:** never removed; the runbook does not cover the capture session yet.
- (CAP design 24, CAP-1 journal, CAP-4 14) The journal: every image a sensor delivers through Mount/Acquire or the capture session is also copied to a journal folder on that computer, which keeps the newest 200 copies. Capture settings can change the number but not below 1, and a 0 typed into the file by hand counts as 200, so the journal cannot be turned off. 8-bit copies are BMP files, lossless, roughly 0.2 to 0.6 GB for 200 copies; a copy that is the only one left is never removed. Are 200 copies, up to about half a gigabyte per computer, right? **Today:** built that way.
- **[BEFORE PATIENT USE]** (CAP-4 4, CAP-4 PS2-4) A journal copy counts as already filed when the patient has an X-ray whose audit entry names the same capture ID, or any image of that patient created within 1 s of the copy's exposure time. There is no image comparison, so an X-ray deleted on purpose no longer matches and its copy is offered again. Outside a session (Imaging Devices, Unassigned captures) the list still shows copies that were filed; Reassign refuses them when either patient already has an X-ray of that exposure, so no duplicate results. Acceptable? **Today:** built that way.
- **[BEFORE PATIENT USE]** (CAP-4 16) A capture reassigned to another patient is filed with the description "Reassigned capture", so the first patient's name never shows in the second patient's chart; the audit trail of both patients names both, with the reason. Confirm? **Today:** built that way.

## 16-bit X-rays and DICOM

16-bit X-rays keep the sensor's full detail. You decided on 2026-11-01 that the program asks for 16 bits by default and may fall back to 14 or 8 ([Device.N] Bits=16 and [Twain] Allow16Bit=1 are now the defaults; Allow16Bit=0 still keeps a computer at 8 bits), and that one Test capture covers every computer that uses the same device row and runs the same sensor driver version with the same image settings (Bits, ByteOrder16, Polarity); a computer with its own device row needs its own Test capture, and only the latest record for a device row counts, so after a Test capture for a new driver version, computers still on the old version take 8 bits until they are updated. The capture session still takes more than 8 bits only when the capture settings were saved in Capture settings on that computer, such a Test capture passed at that depth, and the X-ray goes into a mount slot with tooth numbers; otherwise it takes 8 bits and the session window says why ("8-bit (fallback: ...)"). The record must have passed at the depth asked for. A sensor whose driver lists 14 bits but not 16 gives 14 to its Test capture with the default Bits=16, and the session then asks that driver for 14, so no one has to set Bits=14 by hand. 14-bit data is stored unchanged in a 16-bit DICOM file. The display fixes (CAP-W1, CAP-W2), the in-house DICOM reader (CAP-DR) and claim attachment of DICOM X-rays land on main in the same merge step as CAP-16, before any release, so they are not a clinic step (CAP-16 1 under Not asked here). 16-bit X-rays are still not for patient use until counsel has reviewed the 16-bit labelling and the computed window and the clinic run has signed off; until then, computers that capture for patients are set to Allow16Bit=0 (runbook section 14, "Before 16-bit X-rays for patients").

- **[BEFORE 16-BIT]** (CAP design 6; see M2-IMG 2 under Imaging) 16-bit X-rays need two display fixes first: DICOM thumbnails, and cropping and rotating DICOM images (CAP-W1); and brightness scaling that is right for true 16-bit values (CAP-W2, the 16-bit windowing that M2-IMG 2 asks about). The design recommends doing both now, as two small packages. The other choice is the thumbnails only, with only sensors whose values fit in 12 bits, until the later imaging work brings the 16-bit scaling. Do both now? **Today:** both are built, with the design's recommendation (do both now) applied as the default on 2026-11-01 (package TWAIN-W, branch pre/twain-w-1, docs/port-notes/TWAIN-W.md). DICOM X-rays now get thumbnails and are cropped, rotated and flipped like other images (CAP-W1). The brightness scaling for true 16-bit values was already on main from the M2-IMG port; TWAIN-W added the reading of old stored brightness values above 255 on the 12-bit scale, for display only, without rewriting them (CAP-W2). 16 bits are the default since 2026-11-01 (CAP-16), taken once a Test capture covering the sensor passes; computers that capture for patients stay at Allow16Bit=0 until counsel and the clinic run sign off. Nothing has been checked with a real 16-bit sensor image.
- **[BEFORE 16-BIT]** (CAP design 7) Reading DICOM. The DICOM library the program uses today (fo-dicom) has a licence (MS-PL) that does not fit the program's GPL licence, and storing 16-bit X-rays as DICOM leans on it more. The design recommends an in-house reader for the simple DICOM files the program writes, in place before 16-bit DICOM becomes the stored original; other DICOM files keep using fo-dicom until you decide otherwise. Or another library (licence to check), or keep fo-dicom for everything? **Today:** built, with the design's recommendation (the in-house reader) applied as the default on 2026-11-01 (package TWAIN-W, branch pre/twain-w-1; not merged yet). The program's own reader, written from the public DICOM standard, opens the simple uncompressed files the capture writes, and any other file in that same simple form, without fo-dicom. Every other DICOM file (compressed, color, signed, several frames, other encodings) still goes to fo-dicom exactly as before, so fo-dicom still ships.
- **[BEFORE 16-BIT]** (CAP-3 1, CAP-3 2) Polarity. If a sensor's 16-bit values turn out to have black and white the other way round, Polarity=Invert in Capture settings turns them around before the DICOM file is written: zero stays zero and every other value is mirrored, so it can be undone exactly. It applies only after Test capture verified it and that was logged, whatever the sensor says about its values; without it, values the sensor labels "zero is white" are refused. 8-bit X-rays are never inverted. Confirm, as part of the counsel list (CAP design 18)? **Today:** built that way; no real 16-bit sample has been seen.
- (CAP-3 3, CAP-4 2, CAP-4 left open) Settled on 2026-11-01 with the 16-bit filing route, no longer a question. A 16-bit X-ray goes into its own empty mount slot as 16-bit DICOM when the session could store it at its depth now, and is then never turned into an 8-bit image there; when it could not, it goes into that slot as the explicit 8-bit copy (CAP-16 2 under Not asked here). One that cannot go back into its own slot (the slot taken, the mount deleted, no mount, or reassigned to another patient) is filed from unassigned captures as an explicit 8-bit copy: a gray PNG made with the brightness window the session shows, as an unmounted "Recovered: <slot>" item (or a single document when the mount is gone), with the slot's teeth when the slot is known and none when it is not. The confirmation says plainly that the copy is 8-bit and that the 16-bit original stays in quarantine-resolved; the audit entry says "8-bit copy of a 16-bit capture". Nothing is deleted, Assign goes only to the patient the X-ray was taken for, and Reassign still needs a patient search and a reason. **Today:** built that way.
- **[BEFORE 16-BIT]** (CAP-3 4) A slot whose teeth mix front and back teeth, or back teeth of both sides (for example teeth 5 and 6, a premolar and a canine), has no single view, so its X-ray is taken at 8 bits, like a single image without a mount. None of the standard templates has such a slot. Confirm? **Today:** built that way.
- **[BEFORE 16-BIT]** (CAP-3 7) 16-bit DICOM X-rays are never sent to Pearl, even in a category set for automatic upload, and get no extra audit entry for the sensor's serial number and model, because the file holds them (8-bit X-rays get that entry). Confirm? **Today:** built that way. The explicit 8-bit copy of a 16-bit X-ray (the filing route above, in its own slot or outside it) is not sent either.
