# Port note: S2-1 (central package versions; the identical packages replace their HintPaths)

Package S2-1 of stage 2 of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S2-1 row): branch `net10/s21-1`
from `main` (`81e701df5`). The projects that named one of the files of `Required dlls` whose NuGet package holds the same bytes now
reference that package through central package management, restored from the offline folder with lock files. The build output is the
same (section 4). No program code and no schema change; nothing was downloaded; no program was started. MySqlConnector (2.3.7, S2-2),
the WebView2 files (S2-3) and the other files of `Required dlls` keep their HintPaths; the files of these packages stay in
`Required dlls` until S2-4 moves the release tooling to the packages.

What it changes: the compiler resolves those references to mscorlib's ValueTuple types through it, and reference resolution treats
System.ValueTuple as an assembly of the framework. What it does not change: no compiled assembly (every SDK-style assembly is byte for
byte `main`'s, section 4, so no IL, metadata or assembly reference moved); no output folder (a facade is a reference only and is never
copied: no `System.ValueTuple.dll` is in any `bin` folder after the build); no config (reference resolution's suggested redirect to
4.0.5.0 is dropped by `ODDropValueTupleRedirect` in `Directory.Build.targets`, as before S2-1, and every `.config` keeps its bytes);
nothing staged by `Build-Release.ps1`. At run time System.ValueTuple binds to the framework's copy, as `RequiredDllsTests` checks. The
lock files name 27 packages in all; each `.nupkg.metadata` content hash in the offline folder is the one the lock files record.

**Why transitive pinning.** Without it NuGet takes the lowest version a package asks for: MSAL 4.92 for .NET Framework 4.7.2 asks for
`System.Diagnostics.DiagnosticSource` 6.0.1, `System.Formats.Asn1` 8.0.1 and `System.Text.Json` 6.0.10 (not in the offline folder),
`Microsoft.Extensions.Logging.Abstractions` 8.0.3 for `System.Buffers` 4.5.1 and `System.Memory` 4.5.5, `Microsoft.Extensions.DependencyInjection.Abstractions`
8.0.2 for `Microsoft.Bcl.AsyncInterfaces` 8.0.0. Pinned, every project gets the one file of each assembly that `Required dlls` held,
which the binding redirects of the configs name.

**Why the source generators are off.** `Microsoft.Extensions.Logging.Abstractions` and `System.Text.Json` bring Roslyn source generators,
which the SDK hands the compiler of every project that has the package anywhere in its graph; `ExcludeAssets="analyzers"` on a direct
reference does not take them out. The first build with the packages failed in `PdfSharp-gdi` and `MigraDoc.DocumentObjectModel` with
CS0757 (a partial method with two implementations): their `LoggerMessages.cs` is what the logging generator writes for upstream's
`LogMessages.cs`. `DisableMicrosoftExtensionsLoggingSourceGenerator` and `DisableSystemTextJsonSourceGenerator` (the packages' own
switches, read by their `buildTransitive` targets) are set in `Directory.Packages.props`, so no compiler gets an analyzer it did not get
before (the `/analyzer` arguments of every compilation are unchanged, section 4). When code wants a generator later (on .NET 10, the
framework brings System.Text.Json's), the switch for it goes. **Lead decision (2026-11-09):** both generators stay off repo-wide
through stage 2, for the CS0757 reason; stage 3b (S3b-1, which owns `Directory.Packages.props`) decides whether the System.Text.Json
switch goes once the .NET 10 build uses the framework's generator (`docs/specs/net10-plan.md`, the S2-1 and S3b-1 rows).
