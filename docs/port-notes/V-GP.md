## What was built

### Business layer (`OpenDentBusiness/VendorDirect/GlobalPayments/`, compiled by the existing `VendorDirect\**` wildcard)

- `GlobalPaymentsV2.cs`: the program link (`ProgramName.MeetInTheCloud`, row inserted at runtime with `Enabled=0`, description "Global Payments V2"), its programproperty rows, `GetConfig(clinicNum)`, `IsConfigured`, `ShowButton`, terminals, the one-processor rule (`GetEnabledExclusiveConflicts`, `GetExclusiveConflictMessage`), duplicate checks, `SaveCard`, and the note, receipt and security-log text. `GlobalPaymentsV1`: the rename of the program row's description.
  - Settings, per clinic with Headquarters (ClinicNum 0) as the default: `GlobalPaymentsV2AppId`, `GlobalPaymentsV2AppKey` (CodeBase Secrets `osd1$`, masked, high security; an unreadable value counts as not set, a plain value typed into the generic editor is accepted and encrypted on the next save), `GlobalPaymentsV2AccountName`, `PaymentType` (same name as PayConnect's and X-Charge's row, so the Definitions window's "payment type in use" check finds it; `RecurringChargerator.CreatePayment` reads it for V2 payments through `GetConfig`, with the Headquarters fallback, see t1 below), `GlobalPaymentsV2PrintReceipt`, `GlobalPaymentsV2PreventSavingNewCC`, `GlobalPaymentsV2ForceRecurringCharge`; practice level: `GlobalPaymentsV2UseSandbox`.
  - A clinic with its own App ID uses its own App ID, App Key and account name; any other clinic uses Headquarters' three (never a mix). The other settings fall back to Headquarters one by one, wherever they are read (`GetConfig`; the setup window writes a clinic row only when the clinic's value differs from Headquarters').
- `GpV2Client.cs`: the HTTP client. One `VendorHttp` client per host (only `apis.globalpay.com` and `apis.sandbox.globalpay.com`, HTTPS, no Open Dental host), every call a POST and never retried, the access token in memory only (`TokenCache`, refreshed 5 minutes before expiry, one new token and one resend on a 401), the app key never sent (only the SHA-512 secret), `X-GP-Idempotency` on Transactions API calls, redacted log lines only (endpoint, status; never a body, token, key or card token).
- `GlobalPaymentsV2Results.cs`: `GlobalPaymentsV2Result` and a lenient reader of Global Payments' answers (`GpV2Json`): pending detection for device commands, the outcome (approved, declined, failed, cancelled, timed out, unknown), card brand, last four digits, auth code, entry mode, the reusable payment method (`PMT_...` only), expiry.
- `GpV2Transactions.cs`: one transaction start to finish. A terminal sale or refund sends the device command once, then queries `TRANSACTION_LIST` every 2 seconds for up to 180 seconds; a network problem while waiting is retried until the deadline; "Stop waiting" queries once more, so a card charged just before is still recorded, and otherwise reports that the terminal may still finish. A money request that got no answer is reported as "unknown", never resent.
- `RecurringChargerator.GlobalPaymentsV2.cs` (a partial of `RecurringChargerator`): cards saved through V2 (`CCSource` 23 with a token) are charged through the Transactions API (card not present, stored payment method, `stored_credential` RECURRING), sent once with an `X-GP-Idempotency` key equal to its reference. An approved charge gets a payment (`PaymentSource` 23, `ExternalId` = the Global Payments transaction ID, receipt, payment type from `GetConfig` with the Headquarters fallback); a declined one a $0 payment, as the other processors; an unknown outcome is marked failed with no payment and tagged in doubt, which blocks the card in every later run until a person confirms a retry in the Recurring Charges window's own question (see "Recurring charges in doubt" below; Force Duplicates never retries one). The same card is not charged the same amount twice on one day unless duplicates are forced (the window's box; for automated runs the clinic's "Recurring charges force duplicates by default"). The method never throws, so one card can't stop the batch.

### Recurring charges in doubt (t1)

Every run inserts new `recurringcharge` rows, so a reference built from the row number is new on every run and can't, by itself, stop a second charge. And `CreditCards.GetRecurringChargeList` lists a card again whenever its latest attempt has no payment. So an attempt whose outcome is unknown (a 5xx, a timeout, an answer this program can't read, or an approval whose payment could not be saved) is recorded like this:

- The row is `ChargeFailed`, with `[GPV2-IN-DOUBT <reference>]` in `ErrorMsg` (`GlobalPaymentsV2.RecurringInDoubtTag`, never translated; the reference also lets the office look the charge up at Global Payments).
- `GlobalPaymentsV2.GetRecurringChargeInDoubt(creditCardNum)` returns the card's latest tagged row that no later row with a payment has settled (a later approval, or a decline with its $0 payment, is a definite answer from Global Payments on that card).
- While it returns a row, the card is not charged: not by an automated run, not by a manual run, with or without Force Duplicates. The row is marked failed with the earlier attempt's date, amount and reference and what to do (send it again and answer Yes to the in-doubt question); it carries no tag itself (nothing was sent).
- Only a manual run in which a person confirmed that attempt charges it (t3). Before a run, the Recurring Charges window looks up the selected V2 cards in doubt in one query (`GlobalPaymentsV2.GetRecurringChargesInDoubt`, through `RecurringChargerator.GetGlobalPaymentsV2InDoubt`) and, if there are any, asks a separate Yes/No question that defaults to No: it lists patient, date, amount and reference of each attempt (at most 20) and asks whether Global Payments' records were checked and the cards should be charged again. Only Yes fills `RecurringChargerator.SetRecurringChargeNumsRetryInDoubt` with those attempts' `RecurringChargeNum`s; the window resets it before every run. No leaves those cards out of the run (each is marked failed as above); the other selected cards are charged. The confirmation is per attempt and used once: if the retry itself ends in doubt, its new attempt needs a new Yes.
- Force Duplicates is not a confirmation: the window pre-checks it from the clinic's "Recurring charges force duplicates by default", and offices tick it for unrelated reasons (family members sharing a card), so it says nothing about Global Payments' records. It still only decides the same-day duplicate rule.
- Within 24 hours of the attempt in doubt and for the same amount, a confirmed retry reuses the attempt's reference and idempotency key, so Global Payments can answer with the first request's result (an earlier capture is then recorded once) instead of charging again. Later, or for another amount, it is a new request: the person confirming it has checked Global Payments' records.
- Before t3, `canRetryInDoubt` was `_isManual && forceDuplicates`. Since the window is the only caller (`new RecurringChargerator(...,true)` in `FormCreditRecurringCharges`; nothing in this repository runs recurring charges automatically) and pre-checks Force Duplicates from the clinic's setting, every ordinary run in such a clinic retried every card in doubt, and more than 24 hours later with a new key: the double charge the t1 fix was meant to stop. The t1 tests passed `forceDuplicates:false` for the run the window would send with `true`.

INFERRED: Global Payments documents `X-GP-Idempotency`, but the public material read does not say how long a key is kept; 24 hours is assumed. The block itself doesn't depend on it.

### Middle Tier (t1)

The database reads of V2 (`HasSamePaymentOnDate`, `HasSameRecurringChargeOnDate`, `GetRecurringChargeInDoubt`, and from t3 `GetRecurringChargesInDoubt`) start with the usual `RemotingClient.MiddleTierRole==MiddleTierRole.ClientMT` guard (`Meth.GetBool` / `Meth.GetObject`) and use `Db.GetCount` / the CRUD layer, never `DataCore`, so a Middle Tier client runs them on the server. Before t1 they called `Meth.NoCheckMiddleTierRole()` and `DataCore.GetScalar`, which opens a direct connection: every V2 sale from the payment window and every manual recurring run threw on a Middle Tier client. The payment window's duplicate check (`FormGlobalPaymentsV2.ConfirmNotDuplicate`) and its security-log entry can no longer throw out of the async Run handler.

## Partner-gated (needs Global Payments documentation or credentials)

- **Credentials.** Open Dental's setup asks for one "Account Credential" per clinic. Its format is not public; it is presumably issued under Open Dental's own partner arrangement with Global Payments. This fork authenticates with the office's own Global Payments API app (App ID and App Key), the method Global Payments documents publicly. Whether Global Payments gives a dental office production access to Cloud Integration with its own app is not public ("check with your relationship or sales manager for availability").
- **Saving a card on a terminal without a charge** ("Save card" as its own transaction type in the spec): not publicly documented for Cloud Integration, so not offered. Cards are saved only when a sale's answer carries a reusable payment method (`payment_method.id` starting `PMT_`); whether a terminal sale returns one, and what request field asks for it, is not public. Until then "Save card" reports that Global Payments returned no card reference, and recurring charges have no V2 cards to charge (the recurring path is built and tested against the public Transactions API).
- **Finished device-command answers.** The public sample shows the interim answer and a completed command with a `transaction` list, but no declined, cancelled or timed-out answer and no full status list. The reader is lenient and its rules are INFERRED (below); they need checking against the sandbox.
- **Wallet taps (Apple Pay, Google Pay).** These happen on the terminal; nothing in the request distinguishes them. The entry mode is shown when the answer carries it.

## INFERRED behaviours

- `ProgramName.MeetInTheCloud` and `payterminal.CCIntegration` "MeetInTheCloud": the documents call the integration MeetInTheCloud ("UI: Global Payments V2") and say `CCIntegration` holds the integration "e.g. PayConnect" (= `ProgramName.PayConnect`). The real program row name is not published.
- Property names (`GlobalPaymentsV2*`): Open Dental's are not public. A database Open Dental converted to 25.4 or later would not carry over its V2 settings (no such database is adoptable today).
- Token storage: `creditcard.XChargeToken` with `CCSource` 23, as V1 does (the spec's "likely"). Only the last four digits are kept; never the card number.
- The device's `device_reference` is the Terminal ID entered in setup (Open Dental: "the serial number of the card terminal device"; Global Payments: "each device has a unique value").
- `X-GP-Version: 2021-03-22` on every endpoint (the Cloud Integration samples show another date format).
- Amounts in minor units for device commands (the sample's "1234"; documented for the Transactions API).
- Outcome rules: a transaction status decides first (CAPTURED, PREAUTHORIZED, FUNDED approve; DECLINED, REJECTED decline; FAILED, ERROR, FOR_REVIEW fail; CANCELLED, TIMEOUT, EXPIRED cancel; REVERSED approves a void only); then `payment_method.result` ("00" approves, any other code declines); then `action.result_code` (SUCCESS / DECLINED); a COMPLETED command with a transaction ID and no other code is approved; a command that ended without a transaction moved no money. Pending command statuses: blank, INITIATED, PENDING, IN_PROGRESS, PROCESSING, QUEUED, SENT, WAITING, RECEIVED.
- Waiting: queries every 2 seconds, up to 180 seconds (PayConnect terminals use 190).
- Account name for saved-card charges: the configured one, else the first account the access token lists with `TRN_POST_Authorize`.
- Recurring `stored_credential` model/reason RECURRING, sequence SUBSEQUENT; saved-card charges `entry_mode` ECOM, `channel` CNP.
- References: `RC{RecurringChargeNum}-{yyyyMMdd}` for a new recurring charge attempt (also the idempotency key; a forced retry of an attempt in doubt within 24 hours reuses that attempt's reference), `SL`/`RF` + UTC time + random for window charges, `VOID-{transaction}` as a void's idempotency key.
- Recurring charges in doubt: blocked until a later attempt on the card gets a definite answer, and retried only by a manual run after a person answers Yes to the Recurring Charges window's separate in-doubt question for that attempt (neither Force Duplicates nor the clinic's "force duplicates by default" ever retries one); the 24-hour reuse window of the idempotency key. Open Dental's public material doesn't describe this case.
- Duplicate check in the payment window: "same card" can't be known before the terminal reads it, so it is "same patient, same amount, same day, a completed V2 payment", and the user may go ahead.
- The V1 program row's new description is "Global Payments V1" (see Deviations).

## Deviations from the spec

- No fork migration step; the level range 2027005001-2027005099 is unused. The two data changes are done at runtime instead, idempotently, when Setup > Program Links opens: `payterminal.CCIntegration` '' becomes 'PayConnect' (readers treat '' as PayConnect anyway), and the V1 description rename. Reason at the time: levels in the package ranges (month 00) failed `ForkMigrationRunner.ValidateStep` on that base. On `port/int-8` the validator accepts package levels (`IsReservedPackageLevel`, from M2-UDS), but a step that changes rows on an adopted 25.3.48 database would also need the M1-Z adoption tools to expect it (migration-preview, `AdoptionRowCheck`); the runtime change is outside the migration, idempotent, and harmless (readers treat '' as PayConnect), so t1 keeps it and the adoption tools are untouched.
- Program descriptions are "Global Payments V1" and "Global Payments V2", without the "from www.globalpaymentsintegrated.com" of Open Dental's list (ground rule 7: no vendor web addresses; same as the other vendor-direct rows).
- Credentials: App ID + App Key (+ optional account name) instead of one "Account Credential" (see Partner-gated).
- Business files live in `OpenDentBusiness/VendorDirect/GlobalPayments/` instead of `WebBridges/GlobalPaymentsV2`, so the shared `OpenDentBusiness.csproj` needs no edit (wildcard).
- `PayTerminals.Refresh(clinicNum)` now returns PayConnect terminals only ('' or 'PayConnect'), so the PayConnect windows (V-PC's files) filter without being edited. `PayTerminals.GetForIntegration` is the general call.
- No V2 option in Credit Card Manage's "Add" (saving a card without a charge is partner-gated) and no V2 button in the insurance payment window (`FormClaimPayEdit`, prepaid cards); the V1 panel there keeps its 24.3 text.
