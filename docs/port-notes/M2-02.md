## The EnumPermType 272 conflict

Evidence, all from the published documents (the `grouppermission.PermType` enum list):

- OpenDentalDocumentation25-3.xml: 264 ImageSignatureCreate through 271 EFormImport, then **272 PhoneExtension** (HQ only). The 25.3 diff document also lists 272 PhoneExtension.
- OpenDentalDocumentation25-4.xml and OpenDentalDocumentation26-1.xml: **272 BlockoutAdd, 273 BlockoutDelete, 274 PhoneExtension, 275 PatientSelected**; 26.1 adds 276 LogScraperHQ.
- OpenDentalDiffDocumentation25-4.xml lists 13, 77, 78, 81, 272, 273 and 275 but not 274. The documentation builder compares members by name, so a renumbered member with an existing name is not shown. That is why the specs saw only "272 is PhoneExtension in 25.3 and BlockoutAdd in 25.4".

Conclusion: Open Dental 25.4 moved PhoneExtension from 272 to 274. This program follows 26.1: 272 BlockoutAdd, 273 BlockoutDelete, 274 PhoneExtension (still reserved and hidden), 275 PatientSelected, 276 LogScraperHQ. `tests/M202Tests/Data/OdEnums26_1Changes.txt` records the numbers with their sources, and `EnumRegistry26_1Tests.Permission272_FollowsThe25_4And26_1Documents` checks the 25.3 reference data against them.

Data: an office database from 25.3.48 can hold `grouppermission` rows with 272 meaning PhoneExtension: Open Dental's own Set All grants every permission, HQ-only ones included. Seed26_1 moves those rows to 274 before it grants BlockoutAdd, so they keep their 25.3 meaning and nobody gets BlockoutAdd by accident. `securitylog` rows with 272 are hashed and never edited; the step only counts them in its log (an office database should have none, because only HQ writes PhoneExtension entries).

## Seed26_1 (level 2026102501)

1. Preference rows with their defaults, on every database that lacks them; an existing row is never changed. Open Dental publishes no preference names, so no Open Dental database has these exact rows.
2. On a database from before 25.4 (24.3, or an Open Dental 25.3 database adopted by the fork; judged by `ForkAdoptedFrom` on an adopted database, otherwise by `DataBaseVersion`, unknown origins never converted): the 272 to 274 move above, then BlockoutAdd and BlockoutDelete for every user group that holds Blockouts (13), copying FKey, NewerDate and NewerDays, and only when no row for the new permission exists yet. This is the spec's fork decision; Open Dental's own 25.4 conversion is not public.
3. The permission part runs once per database: on a `RunAll` rerun the runner has already recorded the level, and 272 then means BlockoutAdd, so the step skips it. A second run changes nothing (tested).

The step is in namespace `OpenDentBusiness.ForkMigrations.Seeds26_1`, because `HandOffIntegrationTests` requires every step in `OpenDentBusiness.ForkMigrations` to sort before `Seed25_3Step`.

- Account Module Service Date View (category 22): default columns are the 24.3 Service Date View window's (Service Date, Trans Date, Patient, Reference, Charge, Production, Prov, InsBal, AcctBal, same widths); Clinic is available. - Treatment Plan "Cat% UCR": the internal name stays (stored rows use it). The available entry carries the description "Cat% Std Fee", and `DisplayFields26_1.GetColumnText` returns that text for saved rows without a description. INFERRED short form of "standard provider fee".

## Employee Titles (DefCat 56)

M2-01 owns `Def.cs`, so the DefCat member may not exist on this branch. `DefCats26_1.EmployeeTitles` is the constant `(DefCat)56`; `DefL` and `Defs` use it in `case` labels, which keeps working once `DefCat.EmployeeTitles` exists. Rules (INFERRED): titles can be added, renamed, hidden and deleted; a title an employee uses (`employee.Title`, M2-01's column) cannot be deleted, and hiding it shows the usual "in use" warning. `FormDefinitions` needs no change: it lists every DefCat member through `DefL`, so the category appears as soon as M2-01's member is merged.
