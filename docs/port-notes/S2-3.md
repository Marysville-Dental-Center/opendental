## 4. The loader: what the package's build files do, what was set, and why

`build\Microsoft.Web.WebView2.targets` (read from the offline folder) sets `WebView2ProjectKind` to `managed` and `NugetRoot` to the package
folder and imports `build\Common.targets`, which imports `build\wv2winrt.targets`. For a managed project:

- `EffectivePlatform` comes from `PlatformTarget`, x86 for every SDK-style project (`Directory.Build.props`), so only the x86 loader is
  named; the x64 and arm64 loaders are added only for an AnyCPU (or empty) `PlatformTarget`.
- The loader is a **Content item with `Link` `runtimes\win-x86\native\WebView2Loader.dll`** and `CopyToOutputDirectory` `PreserveNewest`:
  a sub folder, not the top of the output. On .NET Framework, `Microsoft.Web.WebView2.Core.dll` finds the loader there too, but the program
  has always had it next to the exe, and `tools\Build-Release.ps1` refuses any sub folder in `OpenPmsDental\bin\Release`.
- **`WebView2LoaderPreference`** (Dynamic by default) decides only for a native project: the flat Content copy and the link settings are
  C++ only. It does not move the managed item, so it is not set. **`WebView2UseWinRT`** is not set either: true would reference the WinRT
  metadata and drop the loader. No package property puts the managed loader at the top of the output.
- `wv2winrt.targets` stays idle (`WebView2UseDispatchAdapter` is not set: no `wv2winrt.exe` run in the build log); `Common.targets` also adds
  a `PropertyPageSchema` (Visual Studio's property page) and a `CleanDownloadContentFiles` target after Clean that deletes
  `$(OutputPath)\WebView2Loader.dll`, which the next build copies again.
- NuGet itself copies the package's native asset of an exe's `win-x86` target (`runtimes\win-x86\native\WebView2Loader.dll`) flat into that
  exe's output, with or without the build files.

**What this package sets:**
1. `Directory.Build.targets`: when the package's targets are imported (`WebView2ProjectKind` managed and `NugetRoot` set),
   `<Content Update="$(NugetRoot)runtimes\win-x86\native\WebView2Loader.dll" Link="WebView2Loader.dll" />`. The item then lands at the top of
   the output folder, and, as a copied Content item, goes on to the output of every project that references the project, exactly as the None
   item of OpenPmsDental did. MSBuild matches the Update by full path, so the item's own spelling (`build\\..\runtimes\...`) does not matter.
2. `ExcludeAssets="build"` on the PackageReference of the two libraries, CodeBase and WpfControlsOD: with the build files, the loader would be
   copied into their output folders and from there into every project that references them (almost all of them). Without, only OpenPmsDental,
   LibWebTests and M2IMGTests, and the projects that reference OpenPmsDental, get it: the same folders as before. The libraries need only
   the assemblies; `ExcludeAssets` does not change what flows on (the build files are private by default).

**How it was checked** (Debug and Release builds of section 7):
- The 32 output folders that had `WebView2Loader.dll` before (Debug and Release alike: OpenPmsDental, UnitTests, CentralManager,
  DocumentationBuilder, LibWebTests, M2IMGTests and the 26 test projects that reference OpenPmsDental) have it after, at the top of the
  folder, with the same SHA-256 (`7dd7dcf9...`, the x86 loader of `Required dlls` and of the package).
- No `runtimes` folder in any output folder of the repository, and no file with the hash of the x64 or arm64 loader.
- New: the loader in 8 more folders (section 7), by NuGet's native asset of their `win-x86` target.
- `ReleaseFlowTests.OpenDentalCsproj_CopiesTheNativeRuntimeDllsInEveryConfiguration` checks the evaluated items of OpenPmsDental for Debug
  and Release: one copied item of the loader, the package's Content item of `runtimes\win-x86\native`, `Link` `WebView2Loader.dll`, its
  bytes those of `Required dlls`; none to a sub folder, no x64 or arm64 loader, no item of `Required dlls`. `OutputFolder_HasTheNativeRuntimeDlls`
  checks the built folder (x86 PE, the bytes of `Required dlls`).
- The staged release has `WebView2Loader.dll` with the same hash (section 7).

## 6. The project-file reader

The reader (`tests/ProjectFileTests/ProjectFile.cs`) reads a package's build files that the restore imports (S2-1), so it now reads the
WebView2 package's for OpenPmsDental, LibWebTests and M2IMGTests. It threw there ("'Current' <= '15' compares no numbers"), and would have
thrown for the Choose and for `$(NETCoreSdkRuntimeIdentifier)` next. Modelled, as MSBuild 18 and SDK 10.0.114 have them:
- **Choose** (`ReadChoose`): the When elements in order, each Condition evaluated until one is true and no further, else the Otherwise; the
  chosen one's PropertyGroups in pass 1, its ItemGroups queued for pass 2, a Choose in it the same way. What MSBuild rejects throws: a
  Condition on the Choose, no When, a When without a Condition, an Otherwise before a When or a second one, any element but PropertyGroup,
  ItemGroup and Choose in a When or Otherwise (an Import there is MSB4067). Before, every Choose threw.
- **`'$(MSBuildToolsVersion)'` in `<`, `>`, `<=`, `>=`**: an operand written exactly so (any case) that expands to `Current` is the Visual
  Studio version of the MSBuild that evaluates, 18.0 (MSBuild's `StringExpressionNode`), so the package's `'$(MSBuildToolsVersion)' <= '15'`
  is false. Another operand that holds `Current` stays no number and throws, as it fails in MSBuild.
- **`NETCoreSdkRuntimeIdentifier`**: set by the SDK's `Microsoft.NETCoreSdk.BundledVersions.props` in `Microsoft.NET.Sdk.props`, before the
  project's own properties: the SDK installed on 64-bit Windows is the x64 one (`win-x64`), on 32-bit Windows `win-x86`; '' for a classic
  project. It was on the not-modelled list; `tools\Test-ProjectFileEvaluator.ps1` now compares it for every project (equal in all 156).
- **`MSBuildAllProjects`** joins the not-modelled list: MSBuild's own imports fill it (the restore's `.nuget.g.props`,
  `Microsoft.Xaml.targets`); the package's files add themselves only for an MSBuild before 16.
- **A plain Include keeps a doubled back slash** (`854bc1e45`): the package writes `$(MSBuildThisFileDirectory)\..\runtimes\...`, and MSBuild's
  `-getItem` prints the Include with `build\\..`; the reader collapsed it, which the baseline check (`ProjectBaselineTests` with
  `OPMS_CHECK_PROJECT_BASELINE=1`) reported for the three Content items. The full path stays normalized, so matching by path is unchanged;
  `/` still becomes `\`.
