## How it works

### Group Note window size (25.4)

- `FormProcGroup.designer.cs`: `ClientSize` 990 x 690, no `FixedSingle` border and no disabled maximize box. Anchors: Notes box Top|Bottom|Left|Right (880 x 231); grid Bottom|Left|Right (864 x 222, so it keeps its height); Add/Remove/Save Bottom|Right; Delete, both signature rows and the permission label Bottom|Left. The top rows (dates, user, Lock, Append, Invalidate) keep their positions.
- `FormProcGroup.ApplyRememberedSize` (Load): the opening size becomes the minimum width (so the second box always fits) and a minimum height of 560 (scaled); a remembered size is scaled to the screen, kept within the minimum and the screen's working area, and the window is re-centered. `FormProcGroup_FormClosed` stores the unscaled size when the window is not maximized.
- `OpenDentBusiness/Misc/LocalWindowSizes.cs` (new): `%LocalAppData%\OpenDental\WindowSizes.txt`, one tab-separated line per window and user. Never throws; a bad file means the default size.

### Procedure Note Merge (25.4)

- `ProcNotes.GetNewestForProc` (new): newest row by `EntryDateTime`, then the highest `ProcNoteNum` (two saves in the same second).
- `OpenDentBusiness/Data Interface/ProcNoteMerges.cs` (new): the rules. `IsMergeNeeded` (a newer row by number or time, and this save writes a note row), `IsNoteRowWritten` (whether this save writes a note row, see below), `GetAddedText` / `GetMergedDefault` (pre-fill), `GetResultText`, `CanEditProcNote` / `CanChangeText` / `IsChoiceAllowed` (who may change the text, see below), `TakeAsBaseline` / `ApplyTheirNote` (the window state after a choice), `IsResignNeeded`, `GetTheirSignersToAlert`, `GetLogPermission` (Edit Note on Completed Procedure for C/EC/EO, otherwise Edit Procedure) and `GetLogText`.
- Whether this save writes a note row: `ProcNotes.IsNoteRowNeeded` is the one rule, and `Procedures.Update` calls it too (its old inline condition, with the text compared exactly). The windows predict it before anything is saved with `ProcNoteMerges.IsNoteRowWritten` (the window's procedure with the note box's text, plus "a signature box changed"). The comparison is exact on purpose: the CRUD stores every note with `\r\n` (`POut.StringNote`) and a RichTextBox returns `\n`, so a save of a multi-line note that changes only the Dx, the fee or the provider still writes a row with the older text; the window asks then. `IsNoteTextChanged` (line breaks ignored) is used only where signatures are concerned, because signature keys ignore line breaks.
- Who may change the text in the merge window: Keep Mine and Save Merged are offered only when the note box was editable in the window and the user may edit the newer note under the window's rule: Group Note Edit Signed rule 4 (`GroupNoteSignatures.CanEditNoteText` on the newer note's two signers) in the Group Note window, Procedure Note Full / Procedure Note User (`CanEditProcNote`, the same rule as FormProcEdit's load) in Procedure Info. Otherwise only Keep Theirs and Cancel are offered and the merged note is read-only; the caller also refuses a choice `IsChoiceAllowed` does not allow. So a co-signer (who may sign box 2 of someone else's note but not edit it) can't change that note's text, or put an older text back over a newer signed note, through the merge window.
- `WpfControlsOD/Frms/FrmProcNoteMerge.xaml(.cs)` (new): the window. Returns `MergeChoice` and `NoteMerged`. With `canChangeText` false, Keep Mine and Save Merged are disabled (and refuse a click or Alt+S), the merged note is read-only and the intro says why.
- Procedure Info: `OpenDental/Forms/FormProcEdit.NoteMerge.cs` (new partial file). `FormProcEdit.cs` has two one-line hooks: `NoteMerge_Load()` at the start of the load, and `if(!NoteMerge_TryResolve()) { return; }` at the start of `SaveAndClose`, before anything is written (it covers Save, Set Complete and Lock).
- Group Note window: `TryResolveNoteMerge` runs after `EntriesAreValid` in Save and Lock.
- After any choice but Cancel, the window's "old" copy takes the newer note's text, user and signatures (`TakeAsBaseline`), and the newer row becomes the new baseline, so `Procedures.Update` compares against what is in the database now and the window does not ask again.
  - **Keep Mine**: my text and my signature (drawn over my text, so it stays valid).
  - **Keep Theirs**: their text, user and signatures are put back into the window (`ApplyTheirNote`: both copies get their text as the note box returns it, so the exact comparison finds no change); no note row is written (tested, also for a `\r\n` note), my other edits are saved. A signature I drew was made over my note, which is not kept: it is dropped and the window stays open so I can sign the kept note (when I may) and save again. When I may not edit the kept note, the note box, the first box, Change User, Append, Auto Note and (Group Note) Delete, date, provider and procedures are locked as when such a note is opened, and box 2 stays usable only when `CanSignBox2` allows it. In the Group Note window, if the date or the attached procedures were changed here, their signatures no longer fit and are cleared; the user is asked to sign again when there were any (or when a signature was drawn). If the user may not edit the kept note and changed the date, the provider or the procedures, Keep Theirs is refused with a message (saving them would change and unsign a note they may not edit); nothing is taken over and the next save asks again.
  - **Save Merged**: the merged text. A signature drawn in the window over a different text is cleared and the window stays open for signing again ("any merge result different from the signed text clears the signature").
  - **Cancel**: back to the window, nothing saved.
- Alerts: when Keep Mine or Save Merged replaces a signed newer note, its signer(s) get the existing "signature cleared" alert when subscribed, unless they are the user at the keyboard or a switched user. In the Group Note window this goes through the existing prompt and alert code (the old copy now holds their signer); Procedure Info alerts directly and skips a signer that its own save code already alerted.
- Audit: one entry per resolved merge, written after the save: "Procedure note merged with changes by X" (Save Merged), "saved over changes by X" (Keep Mine), "changes discarded; kept the note saved by X" (Keep Theirs), under the note's permission (see above).

### Second signature (26.1)

- `OpenDentBusiness/Data Interface/GroupNoteSignatures.cs` (new): the rules. `GetSignatureKey2`, `CanEditNoteText`, `CanSignBox2`, `GetSignersError`, `GetSecondSignerToAlert`, alert and log texts, and the progress notes' Signed column.
- Group Note window (`FormProcGroup.cs`): box 2 is filled with its key on load, cleared with box 1 when the note text, the date or the attached procedures change, saved by `SaveSignature2` (blank box: `UserNum2` 0), checked in `AreSecondSignatureEntriesValid` (auto-note block, invalid signature, different signer), prompts before a saved second signature is removed, alerts the second signer when someone else cleared it, and logs "Second signature by X" / "... cleared" in the group note's Edit Procedure entry. Change User for box 2 logs a domain-login switch like box 1.
- After Keep Mine or Save Merged the old copy holds the newer note's second signature, so the second signer's "signature cleared" alert also fires when the save replaces it without box 2 being touched here (`_hasSig2Changed || ProcNotes.IsSecondSignatureChanged`).
- Saving (`Procedures.Update`): a new note row is written also when the second signature changed (`ProcNotes.IsSecondSignatureChanged`, part of `ProcNotes.IsNoteRowNeeded`, which replaced the inline condition), and `ProcNotes.SetSecondSignature` decides the row's second signature: as the caller set it when changed; none when the text changed (it was made over the old text); otherwise carried from the newest row with the same text. The last rule keeps a second signature when a caller that never loaded it (most procedure readers, for example `GetOneProc`) saves a note with only the first signature changed.
- Loading: the Group Note window gets the procedure from `Procedures.GetOneProc`, which does not select the new columns; `FormProcGroup.LoadSecondSignature` takes them from the newest row when that row is the note shown. So the readers in `Procedures.cs` (owned by M2-HIST in this wave) did not need to change.
- Chart (`ChartModules.GetProgNotes`, three inserted lines): the procnote query also selects `UserNum2` and `Sig2Present`; the Signed column reads "Signed" when only the first box is signed (unchanged), "Signed: A, B" when both are, "Signed: B" when only the second is. Audit mode adds "(signature 2: B)" after a version's header. Printed progress notes print the grid, so they show the same.
- `ProcNotes.GetIsProcNoteSigned` (Account module) counts either signature.
- Incomplete Procedure Notes report (`RpProcNote.GetQuery`, B-SERVER): a note signed only in its second box is not listed as unsigned. Database maintenance, invalid characters (`DatabaseMaintenances.InvalidCharsGdi`, B-DBM): a `procnote` row with a second signature is a signed row and is never changed, since changing the note would invalidate that signature. Both treat a NULL `Signature2` (rows written before the column existed) as unsigned.

## INFERRED behaviour (not public; minimal reasonable choice)

1. **Second signature key.** The spec says both signatures are made over the same key data. The second key uses the same fields (procedure date, entry date, user, note, attached procedures) with the second signer (`UserNum2`) in place of the note's user. Each signature is bound to the note and to its own signer; changing the first box's user does not invalidate the second signature. Open Dental's 26.1 key is not public: a second signature written by Open Dental 26.1 could show as invalid here (no 26.1 Open Dental database can be adopted yet).
2. **Editing a note signed by two.** "Only its signer or Group Note Edit Signed, applied to either signature" is read as: every signed box must be the user's own. So the first signer alone may not edit (and clear) a note the second signer signed, without the permission.
3. **Co-signing.** The second box can be signed by a user who may not edit the text (box blank or theirs, or Group Note Edit Signed), when the note can be saved and the user may sign notes. This is the dentist-and-hygienist case in the release notes.
4. **Second signer different from the first** only when both boxes are signed. The first box's user while it is blank is only the note's author.
5. **Merge whenever the save writes a note row.** The spec asks for the merge only when the user changed the text. A save that writes only a signature, or (because the CRUD stores notes with `\r\n` and the note box returns `\n`) a save of a multi-line note that changes only another field, also writes a new note row with the older text, so it would put the older text back over the newer one; the window asks in those cases too. It does not ask when the save writes no note row.
6. **Older automatic merge.** When the office has `ProcNoteConcurrencyMerge` on (the 24.3 custom merge in `Procedures.SetNote`), the merge window is not shown and notes merge as before.
7. **Window size per user on the workstation**, in a local file, not in the database: screens differ between workstations, and there is no generic per-user window-size registry entry (`UserOdFkeyType` is foundation-owned and an Open Dental number could collide).
8. **"Printed progress notes print a second signature line"** is met by the Signed column, which is part of the printed grid. The Print Day page keeps its single blank "Signature____" line for a hand signature.
9. Audit texts and the permission for the merge log (Edit Note on Completed Procedure for completed notes, otherwise Edit Procedure) are this fork's wording.
10. **Who may change the text in the merge window** (fix round t1): the note's own edit rule, applied to the newer note, and only when the note box was editable in the window (`ProcNoteMerges.CanChangeText`). Otherwise only Keep Theirs and Cancel. The spec lists the four buttons without saying who may use them; rule 4 of the 26.1 spec and Procedure Info's note permissions decide it here.
11. **Keep Theirs with a signature drawn here**: the signature was made over my note, which is not kept, so it is dropped and the window stays open for signing the kept note again ("any merge result different from the signed text clears the signature, and the user must re-sign"). Keep Theirs over a note the user may not edit, after changing the group note's date, provider or procedures, is refused with a message.
12. **Second signature in the report and in database maintenance**: a note signed only in its second box counts as signed (not listed as unsigned; never changed by the invalid characters fix), as in the Chart.

## Deviations from the spec

- Merge on any save that writes a note row, not only on a text change (INFERRED 5).
- Keep Mine and Save Merged only for a user who may edit the newer note (INFERRED 10).
- Second key with its own signer (INFERRED 1).
- The `SELECT * FROM procnote` readers in `Procedures.cs` were not changed (M2-01's note listed them as M2-NOTES work); the Group Note window loads the second signature itself and `Procedures.Update` carries it, which covers every save path without touching M2-HIST's file more.

## Review findings, fix round t1

1. **The merge window got round Group Note Edit Signed (rule 4).** A co-signer, whose note box is read-only, could sign box 2, get the merge window when a newer row existed, and save any text with Save Merged, or put the older text back over a newer signed note with Keep Mine. Fixed: Keep Mine and Save Merged are offered only when the note box was editable and the user may edit the newer note (`ProcNoteMerges.CanChangeText`: rule 4 on the newer note's two signers in the Group Note window, the Procedure Note Full / User rule in Procedure Info); the caller refuses any other choice; Keep Theirs drops a signature drawn over my note and locks a kept note the user may not edit; Keep Theirs after a date, provider or procedure change over such a note is refused. Tests: `CoSigner_CannotChangeAnotherUsersSignedNote_ThroughTheMergeWindow`, `TextChange_OnlyWhenTheNoteWasEditable_AndTheNewerNoteMayBeEdited`, `ProcedureInfoRule_ForTheNewerNote`, the wiring tests.
2. and 3. **"This save writes a note row" ignored line breaks; `Procedures.Update` does not.** Confirmed, and wider than the review said: the CRUD stores every note with `\r\n` (`POut.StringNote`), so every multi-line note was affected. A Dx-, fee- or provider-only save after another user's newer note silently put the older text back on top, and Keep Theirs wrote a row after all. Fixed: one rule, `ProcNotes.IsNoteRowNeeded` (exact), used by `Procedures.Update` and predicted by both windows with `ProcNoteMerges.IsNoteRowWritten`; Keep Theirs puts their note into both copies as the note box returns it (`ApplyTheirNote`). The rules test that encoded the normalized behaviour now covers only the signature use (`NoteTextChanged_IgnoresLineBreakStyle_ForSignatures`); new rules and database tests run the real `Procedures.Update` against the prediction (`Merge_CrLfNote_OtherEditOnly_PredictionMatchesProceduresUpdate`, `Merge_CrLfNote_KeepTheirs_WritesNoRow_AndKeepsTheirSignature`).

## Owner questions

1. Second signature key (INFERRED 1): keep each signature bound to its own signer, or bind the second signature to exactly the first signature's key as the spec words it (then a change of the first box's user would clear the second signature)?
2. Editing a note signed by two (INFERRED 2): should either signer be allowed to edit (clearing the other's signature, with an alert), or only a user with Group Note Edit Signed, as built?
3. Merge on any save that writes a note row (INFERRED 5): keep, or ask only when the text changed, as the spec says (then a signature-only or other-field save of a multi-line note would put the older text back over a newer one)? Alternatively, a save whose text differs only in line breaks could keep the stored text and write no row at all, which would also stop the duplicate note versions 24.3 writes on every such save.
4. Window size: per user on each workstation (built), or per user everywhere (would need a `UserOdFkeyType` value from the registry owner)?
