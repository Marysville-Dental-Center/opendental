# Port note: S2-2 (MySqlConnector 2.6.2 and the Microsoft 10.0 packages)

Package S2-2 of stage 2 of the .NET 10 move ([docs/specs/net10-plan.md](../specs/net10-plan.md), the S2-2 row): branch `net10/s22-1` from
`main` (`20f2ab8a8`). MySqlConnector goes from 2.3.7 (a HintPath to `Required dlls`) to the 2.6.2 package, and the three shipped Microsoft
packages that were on 8.0.x, whose support ended on 2026-11-10, go to 10.0.15, the current 10.0 patch; their binding redirects follow. One
driver change needed code (a connection left `Broken`, section 3.1); the database TLS check of the row is a new test that runs once its
environment exists (section 6). Everything came from the offline folder (download batch A, approved by the owner, fetched and checked by
the lead); nothing was downloaded and no program was started. WebView2 (S2-3), `Build-Release.ps1`, `THIRD-PARTY-NOTICES.txt` and the
deletions from `Required dlls` (S2-4) are untouched.

Commits: `7d77206ee` (packages, projects, configs, `Required dlls`, lock files), `9a98f90f0` (code), `9ffe42e3a` (tests), and this note; the
review round on `net10/s22-2` (section 11); the follow-up round on `net10/s22v-1` (DB-SEC 3, section 12).

## 3. The 2.4 to 2.6 review

**What could be read.** The `.nupkg` carries no release notes: its `releaseNotes` element is only the link
https://mysqlconnector.net/overview/version-history/, and its `README.md` is the usage text. The upstream source (repository
`mysql-net/MySqlConnector`, commit `775689bb3e1ab55d16171e0795264fa746e364c4` per the nuspec) cannot be read without a download, and neither
can the advisory GHSA-473q-m89c-ghf8. **Not checked, therefore:** the version-history text itself, the advisory's description, and any change
that neither the assembly's public surface nor its IL in the paths below shows. **Checked instead** (with the 2.3.7 file of `Required dlls`
and the 2.6.2 file of the package, outside the repository):
- the public API of both assemblies with Mono.Cecil: 1,761 public types and members in 2.3.7, 1,820 in 2.6.2, **none removed**;
- the IL of the TLS set-up (`ServerSession.InitSslAsync`, its certificate callback, `ConnectAsync` after the authentication);
- the behaviour of both builds on the local MariaDB (127.0.0.1:3306, root, no database created): the program's connection options, a session
  killed under an open connection, a killed pooled session, `KILL QUERY` during a query, `ResetConnectionAsync` on a killed session, argument
  checks, a wrong user and an unknown database;
- and then the tests of section 7 against 2.6.2 in the build.

Item by item:

### 3.1 `State=Broken` after a network error

- **Found:** after its session is killed, the next command throws `MySqlException` (Number 0, "Failed to read the result set.", inner
  `SocketException`) in both versions. 2.3.7 then reports `State=Closed` and `Open()` works again; 2.6.2 reports `State=Broken`, and `Open()`
  throws `InvalidOperationException` "Cannot Open when State is Broken." until `Close()` (then `Closed`, and `Open()` works).
- **The program's reconnect logic** (`DataConnection`): `RunDbAction` closes the connection on every exception it sees, and the retries
  (`RetryQuery`, the `IsErrorHandled` paths of `GetTable`, `GetList`, `NonQ`, `GetCount`, `GetScalar`) close before they open again, so those
  paths behave as before. Not covered: an exception that does not come through `RunMySqlAction` (in `GetCount`, `_dr.Read()` and `_dr[0]` run
  outside it) leaves the connection `Broken`, and a `DataConnection` that is used again (long-lived ones exist: MySQLManager's forms keep one)
  failed on its next `Open`. **Changed:** every `_con.Open()` of `DataConnection` (six) goes through `OpenCon`, which closes a `Broken`
  connection first. The message checks of the reconnect logic (`IsConnectionLost`: "stream" and "failed", 1042, 1045; the retry on "fatal
  error" or "transport connection") read the same texts in both versions; a killed session's "Failed to read the result set." was and is not
  one of them.
- **Other code:** `PP_LedgerItemGenerator` closed its connection only when `Open`; a `Broken` one was left to the garbage collector, now it is
  closed. `DataConnectionCancelable` (user queries) closes in `finally`, and `KILL QUERY` leaves the connection `Open` in both versions (error
  1317). `ODR.DataConnection` creates a new connection for each report call. `FormDatabaseCheck` (DatabaseIntegrityCheck) keeps one connection
  open for its window; after a network error it fails its next command in both versions, only with another message. No code tests
  `State==Closed` before `Open`.
- **Tests:** `KilledSession_LeavesTheConnectionBroken_OpenThrowsUntilItIsClosed`, `DataConnection_ItsConnectionBroken_ReconnectsOnTheNextQuery`
  (which fails without `OpenCon`: checked by undoing it, `.git\od-tools\test-results\s22-1-mutation.txt`) and
  `DataConnection_SessionKilledDuringAQuery_ThatQueryFails_TheNextOneRuns` (the plan's "a killed connection reports `Broken` and the program's
  reconnect path recovers").

### 3.2 `ResetConnectionAsync` throws `MySqlException`

On a killed session 2.3.7 let the `SocketException` through; 2.6.2 throws `MySqlException` "Failed to reset connection" and leaves the
connection `Broken`. No code of the repository calls `ResetConnection` or `ResetConnectionAsync`. Pinned by
`ResetConnectionOnAKilledSession_ThrowsMySqlException`.

### 3.3 Stricter argument checks

The checks the probe met throw the same exception types with other texts: `CommandTimeout=-1` (`ArgumentOutOfRangeException`, "The value must not
be negative." for "CommandTimeout must be greater than or equal to zero."), `GetValue` past the last column (`ArgumentOutOfRangeException`,
"The value must be less than 1." for "value must be between 0 and 0"). The same in both: `AddWithValue` with null (DBNull), `GetOrdinal` of an
unknown column (`IndexOutOfRangeException`), `GetString` on an integer (`InvalidCastException`), an empty `CommandText`
(`InvalidOperationException`). No code matches these texts or catches these types around MySqlConnector calls; no public member was removed,
so nothing that compiled against 2.3.7 lost an overload (the build compiled every project with no new warning or error).

### 3.4 `MySqlConnectorLogManager.Provider` obsolete

`[Obsolete]` in 2.6.2 (not in 2.3.7). Nothing in the repository names `MySqlConnectorLogManager`; the program never sets a logger, so no
compiler warning came with the upgrade. Pinned in `ProgramsConnectionOptions_AreReadAsBefore`.

### 3.5 Connection-string options

Every option the program writes parses to the same canonical string in both versions: `BuildConnectionStringStart` (`Server`, `Port`,
`Database`, `User ID`, `Password`, `CharSet=utf8`, `Treat Tiny As Boolean=false`, `Allow User Variables=true`, `Convert Zero Datetime=true`,
`Default Command Timeout`), the rule's TLS options (`SslMode=none|VerifyCA|VerifyFull`, `SslCa`, `CertificateStoreLocation=LocalMachine`,
`CertificateThumbprint`), and those the rule and the tools read or set (`Pooling`, `Connection Timeout`, `ConnectionReset`,
`ServerRedirectionMode`, `SslCert`/`SslKey`, `CertificateFile`/`CertificatePassword`, `TlsVersion`, `Protocol`, the `uid`/`pwd`/`sslmode`
synonyms). None was renamed or removed. One option is new: `SkipCertificateRevocationCheck` (default false, allowed only with `VerifyFull`);
the program does not set it, so `VerifyFull` checks revocation exactly as 2.3.7 did (the IL: `checkCertificateRevocation` is
`SslMode==VerifyFull` in both, `&& !SkipCertificateRevocationCheck` in 2.6.2). Character set and sessions: the open with the program's
options reports `utf8mb4` as before.

### 3.6 The TLS options DB-TLS uses (`SslMode=VerifyFull`, `SslCa`, client certificates through `ClientCertificateStore`)

Read in the IL of both versions (the package's `lib/net48/MySqlConnector.dll`, with `ildasm` of the .NET Framework 4.8 tools and Mono.Cecil
0.10.3 from the offline folder; 2.3.7 from `20f2ab8a8:Required dlls/MySqlConnector.dll`):
- **Client certificates** from the store by thumbprint (`CertificateStoreLocation`, `CertificateThumbprint`), from a file, or from
  `ProvideClientCertificatesCallback`: no change in their reading; they are options of their own, separate from `SslCa`.
- **The driver's own check with `SslCa`** (`ServerSession.<InitSslAsync>g__ValidateRemoteCertificate|1`): when SChannel reports chain
  errors, the driver builds a chain of its own (`RevocationMode=NoCheck`, `AllowUnknownCertificateAuthority`, the `SslCa` certificates as
  extra store; `<InitSslAsync>d__129` IL_042a-IL_0443) for the top element of SChannel's chain, and clears the chain errors when that
  chain's first status is exactly `UntrustedRoot` and its root is a certificate of the file, byte for byte (IL_0133-IL_0210); `VerifyCA`
  then drops the name mismatch (IL_0212-IL_0225). Revocation: `checkCertificateRevocation` is `SslMode==VerifyFull &&
  !SkipCertificateRevocationCheck` (IL_06d2-IL_06fc), passed to `SslStream.AuthenticateAsClient`; `VerifyCA` asks for none.
- **Since 2.4 the driver decides after the login** (the finding of the review round, section 11). For `VerifyCA` and `VerifyFull` the
  callback keeps the policy errors in `m_sslPolicyErrors` and the SHA-256 of the server certificate and **always returns true**
  (IL_0227-IL_0276); 2.3.7's returned `errors == None`, so its TLS handshake failed and nothing else was sent. In 2.6.2 the login
  (`HandshakeResponse41`, with the account's challenge response) went over that unverified session, and only after the server's OK packet
  was the connection refused (`<ConnectAsync>d__107` IL_1075-IL_119a), unless the login had a password and the OK packet proved that the
  server knows the account's stored hash (`ServerSession.ValidateFingerprint`, IL_10f7: MariaDB 11.4's check for self-signed servers), which
  the driver then accepted with any certificate. No 2.6.2 option turns that off, and while `SslCa` is set the driver ignores the
  connection's own `RemoteCertificateValidationCallback` (`NotUsingRemoteCertificateValidationCallbackDueToSslCa`). Both exposures were
  chosen by an attacker in the middle of the network, whatever the office server's version: (1) with the account's stored hash it was
  accepted with any certificate and saw every query and row, and the challenge response gave it SHA1(password); (2) without the hash it
  still received the challenge response to its own scramble, which a dictionary attack can test offline. Owner decision Q5 did not hold for
  password logins (DB-SEC 3).

**The fix: DB-SEC 3 decided by the lead as (c), the program verifies the server itself before the login** (follow-up round, section 12;
`docs/specs/db-connection-security.md` section 8). The owner's rule Q5 is unchanged, and the owner can still choose otherwise
(`docs/owner-questions.md`).
- **Where.** Every `MySqlConnection` a shipped binary creates comes from `DbConnectionSecurity.NewMySqlConnection` or
  `NewMySqlConnectionWithoutPooling`; both now end in `CreateConnection`, which asks `GetDriverConnectionString`. For a string whose Server
  is over the network (`IsLoopbackConnectorServer` false) with `SslCa` and `SslMode` `VerifyCA` or `VerifyFull`, the driver gets the same
  string without `SslCa` (and without `SkipCertificateRevocationCheck`, which the driver allows only with `VerifyFull`) and with
  `SslMode=Required`, and the connection gets `OfficeCaServerVerifier.ValidateServerCertificate` as its `RemoteCertificateValidationCallback`,
  for the CA of `SslCa`, the host names of `Server`, and `VerifyFull` (host name and online revocation) or `VerifyCA` (chain only, no
  revocation, as the driver did). The rule still checks the program's string (`VerifyFull` with the office CA, section 2.2 of the spec is
  unchanged); only the driver's copy differs, and that copy fails the rule, so a connection made from it again, without the check, never
  reaches the network. Everything else of the string goes to the driver unchanged (the client certificate options, the password, the
  timeouts). A loopback string, and a string without a CA (a read-only or reporting server without a CA preference, `SslMode=none`), go to
  the driver as before.
- **Why the callback's refusal comes before the login (2.6.2's IL).** `<InitSslAsync>d__129` IL_0601-IL_069b: the connection's callback is
  used when there is no `SslCa` and `SslMode` is `Preferred` or `Required` (`UsingRemoteCertificateValidationCallback`); it is passed to
  the `SslStream` constructor (IL_06b9, IL_06c8), and `AuthenticateAsClient(Async)` (IL_086f, IL_08f9) throws `AuthenticationException` when
  it returns false; the driver turns that into `MySqlException` 1042 "SSL Authentication Error" (IL_0a37-IL_0a51), the same type, number and
  outer message as before (`IsConnectionLost` treats it as before; the inner message is now SslStream's). `<ConnectAsync>d__107` awaits
  `InitSslAsync` at IL_0acf and builds `HandshakeResponse41Payload` only at IL_0c44, so nothing of the login is sent to a refused server.
  `m_sslPolicyErrors` is written only by the driver's own callback (IL_0258), so with the program's callback it stays `None`: the check
  after the OK packet (IL_1075-IL_107b) never runs and `ValidateFingerprint` can never be reached, which closes the MariaDB 11.4 stored-hash
  path too. `IsServerIdentityVerifiedForPassword` (`m_isSecureConnection` and `m_sslPolicyErrors == None`) is true for a server the program
  accepted, so the clear-text password paths (`mysql_clear_password`, the full `caching_sha2_password` exchange) go only to a verified
  server, as under a passing `VerifyFull`. `MySqlConnection.Clone`/`CloneWith` copy the callback (the private constructor, IL_0036-IL_003b).
- **The check** (`DataConnectionBase/OfficeCaServerVerifier.cs`), for the server's certificate and the certificates it sent with it:

  | | The driver with `SslCa` (2.3.7 and 2.6.2) | The program |
  |---|---|---|
  | Root | SChannel's chain top, rebuilt; the root must be a certificate of the file | Windows' chain engine with the office CA file as its only trusted roots (`CERT_CHAIN_ENGINE_CONFIG.hExclusiveRoot`: no root of the Windows stores counts), then the root must be a self-signed certificate of the file, byte for byte |
  | Intermediates | the server's TLS message, the file, the Windows stores, AIA | the server's TLS message, the file, the Windows stores; no AIA retrieval (`CERT_CHAIN_DISABLE_AIA`) |
  | Every element | the first status of the rebuilt chain must be `UntrustedRoot`: an expired server certificate passed when the server sent the CA along (only the CA's chain was rebuilt) | no error on any element (trust, signature, dates, which are also checked directly, revocation), except an unknown revocation status |
  | Usage | not checked (the rebuilt chain has no application policy) | valid for server authentication (requested usage `1.3.6.1.5.5.7.3.1`): the shared client certificate, signed by the office CA too, is not a server |
  | Host name (`VerifyFull`) | SslStream's: Windows' SSL policy with the target host | Windows' SSL policy (`CERT_CHAIN_POLICY_SSL`) for each host of `Server` (one must pass; the driver does not tell the callback which host of a list it reached): the subject alternative names' DNS names and IP addresses, the common name only without them; a trailing dot of the host is left out |
  | Revocation | `VerifyFull` asked SslStream for an online check, but for a chain to a CA outside the Windows root store Windows checks no revocation, and the rebuilt chain was `NoCheck`: a revoked server certificate was never refused | `VerifyFull`: online, without the root (`CERT_CHAIN_REVOCATION_CHECK_CHAIN_EXCLUDE_ROOT`, SslStream's setting); because the engine trusts the office CA, Windows does check it. `Revoked` is a refusal; an unknown status (no CRL distribution point, as the server guide's certificates have none, or a CRL server that does not answer) is not (`CERT_CHAIN_POLICY_IGNORE_ALL_REV_UNKNOWN_FLAGS`), as the driver never refused for it. `VerifyCA`: none, as the driver |

  Why not `X509Chain` with the CA as extra store and `AllowUnknownCertificateAuthority` (the lead's sketch): Windows checks no revocation for
  a chain whose root it does not trust. Tried with a throwaway CA and a CRL served on a loopback port by a scratch script outside the
  repository: `certutil -verify -urlfetch` fetched and accepted the CRL, while `X509Chain` (online and offline) reported
  `RevocationStatusUnknown` and `OfflineRevocation` without one request, also with the CRL already in the URL cache. That is also why the
  driver's check never saw a revocation. The exclusive root store is the mechanism .NET 5's `X509ChainTrustMode.CustomRootTrust` uses on
  Windows; the root's bytes and the whole chain are still checked explicitly afterwards. It needs Windows 8 or later; on an older Windows the
  engine cannot be made and every connection over the network with a CA is refused (fail closed).
- **Pools.** MySqlConnector pools sessions by connection string, and a pooled session was verified once, by the check of the connection that
  made it. Two program strings that differ only in `SslMode` or `SslCa` (the main string and a read-only server's string for the same
  server, database and account) give the same driver string; the second check gets `Pooling=false` instead of the first one's pool
  (`DbConnectionSecurity._dictPoolChecks`).
- **The program's string of a connection.** `DataConnection.GetCurrentConnectionString` and `GetReportConnectionString` read
  `MySqlConnection.ConnectionString`, which seeds other connections (child threads, ODR, reports, the Connection Lost retry, the backup);
  they now read `DbConnectionSecurity.GetConnectionString`, the program's string, so what they seed goes through the rule again.
- **Middle Tier.** The Middle Tier server connects through `DataConnection`, so through `NewMySqlConnection`: the same code path on the
  server, with the server's own settings. A workstation in Middle Tier mode makes no database connection.
- **Reports.** The RDL engine created its MySqlConnector connection itself from the provider's class; it now asks the host's
  `RdlEngineConfig.CreateConnection` hook first, which `FormReportForRdl` and `FormReportCustom` set to `DbConnectionSecurity.NewReportConnection`
  (`NewMySqlConnection`), after the existing `CheckConnection` hook. `RdlDesigner.exe`, a developer tool that is not shipped, sets neither.

`SslMode=VerifyFull`, `SslCa`, `CertificateStoreLocation=LocalMachine`, `CertificateThumbprint`), opened through the connection rule
(`DbConnectionSecurity.NewMySqlConnection`), to a non-loopback address of this computer, as a user created `REQUIRE X509` without a password:
- once with a client certificate whose private key is in a CAPI provider (`RSACryptoServiceProvider`) and once with one in a CNG provider
  (`RSACng` or `ECDsaCng`), both in `LocalMachine\My`, where the connection settings tool imports them (`ClientCertificateStore.ImportPfx`);
- each session: encrypted (`Ssl_cipher`), TLS 1.2 or 1.3, `CURRENT_USER()` is the X509 user, and it reads the synthetic row of the test's own
  database (so it is the server the test prepared);
- the same user without a certificate is refused (`AccessDenied`), and with another CA the server is refused (`MySqlException`): the
  verification over this address is real;
- set-up and clean-up through the local test server's loopback connection (127.0.0.1:3306, root, `DevDbTls.Apply`): an `s22_tls_<time>_<id>`
  database with one synthetic row and an `s22_x509_<time>_<id>`@`%` user (`GRANT SELECT` on it), both dropped in `finally`.

**Variables** (names in `TlsCertificateLoginTests`):

| Variable | Value |
|---|---|
| `OPMS_DB_TLS_TEST_SERVER` | a non-loopback address or name of this computer, in the program's notation (`host` or `host:3306`), at which the local test server listens and which its server certificate names; a loopback address, another port or a list fails the test |
| `OPMS_DB_TLS_TEST_CAPI_THUMBPRINT` | the thumbprint of the CAPI-key client certificate in `LocalMachine\My` (spaces allowed) |
| `OPMS_DB_TLS_TEST_CNG_THUMBPRINT` | the thumbprint of the CNG-key client certificate in `LocalMachine\My` |
| `OPMS_DB_TLS_TEST_CA` (optional) | the CA (PEM) that signed the server certificate; without it, the local test server's CA (`DevDbTls.GetCaPath()`: `OPMS_DB_TLS_CA`, else `%LOCALAPPDATA%\OpenPmsDental\DevDbTls\ca.pem`) |

None of the three set: inconclusive (`WithoutTheVariables_TheCheckIsInconclusive_NeverAPass` checks that a run without them never passes).
Some but not all, or a value that is not what it must be (no certificate of that thumbprint, no private key the account can read, a key of the
other provider, no CA file): a failure. It ran here only as inconclusive: the local MariaDB has no TLS yet (the owner has not run
`tools/Enable-LocalDbTls.ps1`).

**How to run it** (once the environment below exists), from the worktree, in a PowerShell window whose account can read the two private keys
(the tool's import gives `BUILTIN\Users` read access; an elevated window can read them anyway):

```powershell
$env:OPMS_DB_TLS_TEST_SERVER='192.0.2.25'          # this computer's non-loopback address (example from the documentation range)
$env:OPMS_DB_TLS_TEST_CAPI_THUMBPRINT='<40 hex digits>'
$env:OPMS_DB_TLS_TEST_CNG_THUMBPRINT='<40 hex digits>'
powershell -NoProfile -ExecutionPolicy Bypass -File <common git folder>\od-tools\run-tests.ps1 -Root . -Mode Targeted -Include DbConnectionSecurityTests -Out <file>
# or only this class, through the lane (after a build):
powershell -NoProfile -ExecutionPolicy Bypass -File <lane>\odbuild.ps1 -Root . -TestOnly -Test tests\DbConnectionSecurityTests\bin\Debug\DbConnectionSecurityTests.dll -TestFilter "FullyQualifiedName~TlsCertificateLoginTests"
```

The variables reach the test host through the runner's process (both runners start vstest as child processes); with them set, the test is a
pass or a failure, never inconclusive.

**The environment it needs, and what is missing today (for the lead and the owner).** O-12 replaced O-8's temporary second server: the
check runs against the local test server on port 3306 once TLS is on there. Three things are not provided by `tools/Enable-LocalDbTls.ps1`
as it is, and the test cannot make them itself without administrator rights or a CA key:
1. **A non-loopback listener.** The script requires and keeps `bind-address=127.0.0.1`; the server must also listen on the address the test
   uses (and only this computer should reach it, for example with the Windows firewall). DB-TLS section 5.6 noted that there is no other
   address to use today.
2. **A server certificate that names that address.** The script's certificate names `localhost` and `127.0.0.1` only; `VerifyFull` to
   another address needs that address (or the computer's name) in the subject alternative names.
3. **Two client certificates signed by the server's CA, one imported with a CAPI provider and one with a CNG provider, into
   `LocalMachine\My`.** The script makes at most one client certificate (`-WithClientCertificate`, waiting for the owner's yes, DB-TLS
   section 10), as PEM files, and discards the CA key at the end of the run, so a second one cannot be made later. The provider is chosen at
   import, for example `certutil -csp "Microsoft Enhanced RSA and AES Cryptographic Provider" -importPFX My <file>.pfx` (CAPI) and
   `certutil -csp "Microsoft Software Key Storage Provider" -importPFX My <file>.pfx` (CNG), each from a `.pfx` of its own certificate.
A follow-up to the script (its owner is DB-TLS; not changed here) could make all three in the enable run: the extra SAN, two client `.pfx`
files, and the `bind-address` change with its listener check. Until then the stage 2 gate cannot run this check; the plan's gate (section 3,
"the database TLS test run once against the test server") depends on it.
